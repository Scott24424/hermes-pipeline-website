한 줄로 말하면, "AI로 꾸린 개발팀"입니다

AI 하나에게 모든 일을 맡기면 자기가 쓴 코드를 자기가 검토하게 됩니다. 이 프로젝트는 회사가 사람으로 팀을 꾸리듯, 서로 다른 회사의 AI에게 역할을 나눠 주고 서로를 견제하게 만듭니다.

1분 요약

발표를 시작할 때 이 다섯 줄만 말해도 전체 그림이 전달됩니다.

  1. 지휘자 Hermes가 작업을 크기(S/M/L)로 나누고 단계마다 알맞은 AI를 호출합니다.
  2. 만든 AI와 검토하는 AI는 다른 회사로 둡니다. 테스트 작성자와 구현자도 분리합니다.
  3. AI가 쓴 코드는 격리된 브랜치(worktree)에만 쌓이고, 운영 코드(main)에는 손대지 못합니다.
  4. 모든 호출·판정·비용은 원장과 해시로 기록되어, 중단돼도 이어서 하고 나중에 검증할 수 있습니다.
  5. 사람은 매 단계를 지켜보지 않고 요구사항·예산·수용·병합 같은 진짜 결정만 내립니다.

01 — 왜 만들었나

AI 코딩 도구는 강력하지만, 혼자 두면 불안합니다

회사 IT 관리자로서 실제 업무 시스템(PC 자산관리)을 AI로 개발하려고 했을 때, 다음 문제들이 먼저 보였습니다.

🪞

자기 코드를 자기가 검토한다

같은 AI가 만들고 검토하면 같은 맹점을 공유합니다. 테스트까지 같은 AI가 쓰면 "통과하도록 만든 테스트"가 됩니다.

⏳

구독 한도에 걸리면 멈춘다

한 회사 AI에 몰아 쓰면 사용 한도에 걸릴 때마다 몇 시간씩 작업이 멈춥니다. 실제로 한 조각 동안 Claude 한도에 다섯 번 걸렸습니다.

🔍

"완료했다"는 말을 믿을 수 없다

AI는 끝났다고 말하지만 응답이 잘렸거나, 형식이 틀렸거나, 테스트가 엉뚱한 이유로 통과했을 수 있습니다. 증거가 필요합니다.

🌀

AI 환경이 매달 바뀐다

새 모델·가격·도구가 계속 나옵니다. 특정 모델에 묶인 구조는 금방 낡습니다. 측정해서 갈아 끼울 수 있어야 합니다.

그래서 세운 다섯 가지 목표

GOAL 1

최적 비용

같은 품질을 더 적은 비용으로. 실패·재시도·리뷰 비용까지 포함한 "완료 작업당 비용"으로 봅니다.

GOAL 2

최고 품질

테스트 통과와 AI 판정만이 아니라 사람의 평가, 수용 후 발견된 결함까지 확인합니다.

GOAL 3

자동화 개발

요구사항 접수부터 계획·테스트·구현·리뷰·보고, 중단 후 복구까지 자동으로 진행합니다.

GOAL 4

여러 공급사 활용

회사별 강점, 교차 검토, 사용 한도 분산을 함께 얻습니다. 현재 4개 공급사를 씁니다.

GOAL 5

지속 반영

새 모델·도구를 같은 평가 묶음으로 측정해, 개선이 확인될 때만 반영합니다.

최적 비용 ≠ 최저 비용. 품질을 낮춰서 아낀 비용은 성과로 치지 않습니다. 또한 관측되지 않은 비용은 0으로 계산하지 않고 "unknown"으로 남깁니다.

설계 원칙

만든 AI와 검토하는 AI를 다르게

가능하면 회사도 다르게 둡니다. 대체 모델을 쓸 때도 지키고, 독립성이 줄어들면 보고서에 공개합니다.

단계 사이는 파일로만 넘긴다

TASK.md → DESIGN.md → SPEC.md → 테스트 → diff. 추적할 수 있고, 중단돼도 이어서 할 수 있습니다.

테스트 작성자와 구현자를 분리

테스트는 구현 전에 먼저, 다른 AI가 씁니다. 구현자는 테스트를 고칠 수 없습니다.

두뇌는 판단만, 기계적인 일은 스크립트가

AI 호출이 가장 비쌉니다. 실행·검사·집계·파일 기록은 스크립트가 맡습니다.

제품 코드를 쓰는 AI는 하나뿐

Codex만 worktree에 쓸 수 있습니다. 나머지는 읽기 전용이며, 테스트도 스크립트가 tests/ 안에만 기록합니다.

자동 대체(fallback) 금지

미리 승인된 표에 없는 모델 교체는 사람이 결정합니다. 한도에 걸리면 기다렸다가 재개합니다.

03 — 작업 흐름

요청 하나가 커밋이 되기까지, 최대 15단계

Hermes는 요청을 받으면 먼저 크기를 분류합니다. 작은 작업은 단계를 건너뛰고, 큰 작업은 설계와 사람 승인까지 거칩니다. 아래 버튼으로 크기별 경로를 비교해 보세요.

Anthropic OpenAI Google 사람 스크립트 / Hermes

✅ 테스트는 "올바른 이유로" 실패해야

5단계 직후 테스트를 실행해 구현이 없어서 실패하는지 확인합니다. 문법 오류·설정 오류·테스트 0개로 인한 실패는 유효한 RED가 아닙니다.

🔁 수정 루프는 최대 2회

판정에서 BLOCKER·HIGH만 고칩니다. 2회 뒤에도 남으면 멈추고 보고합니다. 같은 단계 연속 4회 실패도 사람에게 올립니다.

⏸ 중단돼도 이어서

state.json에 현재 단계·시도 횟수·실제 사용 모델을 기록합니다. 세션이 끊겨도 마지막으로 끝낸 단계 다음부터 재개합니다.

05 — 안전장치와 검증

"끝났다"는 말이 아니라, 증거로 판정합니다

AI의 응답은 종료 코드가 0이어도 잘렸거나 형식이 틀렸을 수 있습니다. 그래서 결과 판정을 일곱 개의 층으로 나누고, 아래 층의 통과가 위 층을 대신하지 못하게 했습니다.

runner
2

잘림·max_tokens·누락 없이 정상 종료

06 — 위임 운영

사람의 개입을 "진짜 결정"으로 줄이는 방법

초기에는 매 호출마다 사람이 승인해야 했습니다. 2026-10-09 위임 규칙을 만들어 기계적인 판단은 위임 구동자가 맡고, 사람은 조각 단위 검토와 실제 결정만 하도록 바꿨습니다.

🤖 구동자가 묻지 않고 처리하는 것

  • 예산 봉투 안의 배분조각마다 호출 상한(봉투)을 받고, 어느 단계에 몇 회 쓸지는 구동자와 Hermes가 정합니다. 실패·빈 응답도 소비로 셉니다.
  • 기계적 결함내용을 바꾸지 않고 엄격한 대조로 검증되는 것만. 예: 패치 줄 수 표기 오류(git apply --recount), 원문 바이트를 둔 채 추출만 다시 하기.
  • 사전 승인된 모델 교체표에 적힌 조건·대상·횟수 안에서만. 예: 테스트 작성이 출력 한도로 실패하면 지정된 대체 모델로.
  • 기술적 표기 선택요구사항·보안·수용 기준에 영향 없는 표기·형식. 모든 선택은 결정 기록에 남깁니다.

👤 반드시 사람에게 올리는 것

  • 예산 소진 · 일일 상한 도달봉투가 바닥나거나 하루 $40 / 미관측 30회에 도달하면 멈춥니다.
  • 요구사항·수용 기준 변경범위 축소·확대, 명세 해석으로 수용 의미가 바뀌는 경우.
  • 표에 없는 모델 교체, roles.json·설정·스킬 변경구동자가 "전달"로 처리하려 했다가 Hermes가 거부한 사례가 있습니다.
  • 병합 · push · 브랜치 삭제 · 기준선 변경, 다음 조각 시작사용자 본인 메시지로만.
  • 같은 단계 연속 4회 실패무한 재시도를 막는 방어선입니다.

09 — 운영하며 배운 것

직접 부딪혀서 알게 된 여덟 가지

발표에서 이야기하기 좋은 실제 사례들입니다. 모두 원장과 결정 기록에 근거가 남아 있습니다.

LESSON 1 · 테스트 품질

테스트 품질은 모델보다 "도구와 피드백"이 정한다

같은 Gemini라도 조건에 따라 결과가 완전히 달랐습니다.

프롬프트 텍스트만 보고 작성무효 테스트 반복
파일을 직접 읽고 실행 결과를 돌려받음교정 1회로 유효 21건
같은 조건, 상태·Git 연동 테스트무효 2회
Claude Sonnet, 읽기 전용 도구 사용3파일 모두 교정 1회 내
LESSON 2 · 판정

"종료 코드 0"은 완료가 아니다

오류 문자열을 인용한 코드를 시간 초과로 오분류하거나, 굵은 글씨 판정 줄 하나 때문에 파서가 멈춘 적이 있습니다. 그래서 판정을 7개 층으로 분리하고, 원본 응답을 고쳐서 성공으로 만들지 않는 규칙을 세웠습니다.

LESSON 3 · AI의 상상력

검증할 수 없는 걸 요구하면 AI는 API를 지어낸다

공개 API로 확인할 수 없는 항목을 테스트하라고 하자, 작성 AI가 존재하지 않는 API를 만들어 냈습니다. 이후 Hermes가 먼저 "검증 가능 / 불가"로 나누고, 불가 항목은 명세 공백으로 보고하게 바꿨습니다. (D-46)

LESSON 4 · 비용

지휘를 비싼 모델로 돌리면 한도가 가장 먼저 바닥난다

지휘 모델은 작업 한 건에 수십 번 호출되고 매번 누적 대화를 다시 읽습니다. 품질을 좌우하는 판정 몇 곳에만 Opus를 쓰고, 지휘 모델은 사용량에 따라 사람이 바꿉니다.

LESSON 5 · 권한 경계

Hermes가 구동자를 거부하는 것은 버그가 아니라 기능이다

구동자가 "사용자 결정 전달"로 모델 교체를 처리하려 하자, Hermes는 본인 메시지가 필요한 사안이라며 거부했습니다. 다음 조각을 확인 없이 시작하려 할 때도 마찬가지였습니다. 경계가 실제로 작동한다는 증거입니다.

LESSON 6 · 모델 평가

싼 모델은 "어디까지 맡길지"를 측정해서 정한다

Gemini 3.8 Flash를 정답이 있는 12개 과제로 평가했습니다. 형식 12/12 유효, 정상 사례 오탐 0/3이었지만 세부 결함은 9/14만 찾았고 근거 없는 MET 판정도 있었습니다. 결론: 주 리뷰어가 아니라 보조 리뷰어로만 배치. (D-90 → D-94)

LESSON 7 · 공급자 실측

벤치마크 순위보다 우리 과제에서의 성적

DeepSeek은 Node·단순 테스트는 잘했지만 Python 어댑터 내부에서는 반복 실패했습니다. MiMo는 4번 모두 시간 초과로 보류, 한 Gemini 모델은 사용 한도 소진으로 제외했습니다. 사다리 순서는 인상이 아니라 기록으로 바꿉니다.

LESSON 8 · 운영 요령

작은 운영 실수가 몇 시간을 날린다

자정 대기(sleep)와 Hermes 실행을 한 명령에 묶었다가 명령 시간 한도로 Hermes가 죽은 적이 있습니다. 실패한 다른 모델의 초안을 새 작성자에게 넘기면 실수가 전염됩니다. 이런 함정은 모두 인수인계 문서에 남겼습니다.

Hermes 오케스트레이터

여러 AI 도구를 순서대로 호출하고 결과를 관리하는 에이전트입니다. 이 프로젝트에서는 dev-pipeline 스킬을 따라 단계를 진행하고, 규칙·예산·증거를 관리하는 "팀장" 역할을 합니다.

위임 구동자 Delegated Driver

사람 대신 Hermes에 지시를 보내고 결과를 읽는 AI(Claude Code 또는 Codex)입니다. 규칙에 정해진 범위 안에서만 결정하고, 나머지는 사람에게 올립니다.

조각 Slice

큰 개발을 검증 가능한 단위로 나눈 것입니다. 조각마다 호출 예산이 따로 있고, 끝나면 사람이 수용 여부를 검토합니다.

worktree 격리 작업 폴더

같은 Git 저장소의 다른 브랜치를 별도 폴더로 꺼내 쓰는 기능입니다. AI는 이 폴더의 agent/<run-id> 브랜치에서만 작업하므로 원본(main)은 안전합니다.

유효 RED 올바른 실패

구현 전에 쓴 테스트가 "기능이 아직 없어서" 실패하는 상태입니다. 문법 오류나 설정 오류로 실패하는 것은 인정하지 않습니다. RED → 구현 → GREEN이 TDD의 기본 흐름입니다.

봉투 Budget Envelope

조각 하나에 쓸 수 있는 AI 호출 횟수 상한입니다. 안에서의 배분은 위임하고, 다 쓰면 사람이 증액을 결정합니다. 실패한 호출도 소비로 셉니다.

판정 · 수용 Judge · Accept

판정은 리뷰어들의 지적이 실제 diff에 근거가 있는지 가려 등급(BLOCKER/HIGH/MEDIUM/LOW)을 매기는 것, 수용은 수용 기준을 하나씩 증거로 확인해 최종 합격을 정하는 것입니다.

원장 · 등록부 Ledger · Registry

원장은 모든 호출·소비·결과를 시간순으로 적은 기록, 등록부는 효력이 있는 결정·규칙·기준선의 해시 목록입니다. 둘 다 덮어쓰지 않고 이전본을 보존합니다.

SPEC 명세

함수 시그니처, 동작, 오류 처리, 테스트 목록까지 구현 전에 정해 두는 문서입니다. 테스트 작성자와 구현자는 같은 SPEC을 보고 따로 일합니다.

agy Antigravity CLI

Google의 에이전트 CLI입니다. 이 파이프라인에서는 Gemini 모델(및 일부 Claude 모델)을 계획 모드·샌드박스로 호출하는 통로로 쓰며, 코드 실행 권한은 주지 않습니다.
