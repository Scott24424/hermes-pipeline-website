01 / ONE-MINUTE OVERVIEW

한마디로, "서로 다른 AI들로 꾸린 소프트웨어 개발팀"입니다

개발을 전혀 모르는 분도 이해할 수 있도록 레스토랑 주방에 비유해 보겠습니다. 한 사람이 메뉴 개발부터 요리, 위생 검사까지 혼자 다 하면 실수를 걸러낼 수 없듯, AI도 역할을 철저히 나눴습니다.

입문자용 핵심 요약

왜 AI를 여러 명 쓰나요?

AI 한 명에게 "코드 짜고 테스트도 해봐"라고 시키면, 자기가 잘못 이해한 내용 그대로 테스트를 짜서 100점이라고 보고합니다.

그래서 문제 출제자(테스트 작성 AI)와 문제 풀이(코드 구현 AI), 채점관(리뷰·판정 AI)을 아예 다른 회사의 AI로 분리했습니다.

작성자 ≠ 검토자 ≠ 판정자 원칙

02 / MOTIVATION & GOALS

내가 무엇을 하고 싶었는가 — 기존 AI 개발의 4가지 한계

사내 실무 시스템(약 1,000명 규모 PC 자산관리 웹앱)을 AI로 개발하려다 보니, 단순히 채팅창에 코드를 물어보는 방식으로는 넘을 수 없는 벽이 있었습니다.

① "AI 중계 노동"에서 벗어나고 싶었습니다

초기에는 사람이 직접 AI에게 설계를 시키고, 그 결과를 복사해 다른 AI에게 리뷰를 시키고, 에러 로그를 다시 붙여넣는 수동 중계 작업이 단계의 대부분을 차지했습니다. 사람이 자리를 비우거나 노트북을 덮어도 서버(Mac)에서 알아서 다음 단계로 넘어가고, 멈춘 지점부터 이어 달리는(--resume) 자동화가 필요했습니다.

② 한 모델의 "착각 공유"와 "거짓 완료"를 막고 싶었습니다

한 AI가 코드와 테스트를 함께 짜면 요구사항을 잘못 읽은 부분까지 똑같이 통과합니다. 심지어 설정 오류나 오타 때문에 테스트가 아예 돌지도 않았는데 "실패 테스트(RED) 확인 완료!"라고 보고하는 일도 벌어졌습니다. 기계적인 런타임 증거 없이는 AI의 말을 믿지 않는 구조가 필요했습니다.

③ 특정 AI 구독 한도(Quota)에 발목 잡히지 않고 싶었습니다

Claude Code와 Codex(ChatGPT)에 작업이 몰리면 5시간 사용 한도에 걸려 개발 전체가 멈춥니다(실제로 조각 2에서 4번 정지). 반면 같은 시점 Google Gemini 한도는 100% 남아 있었습니다. 여러 AI 공급사로 역할을 분산하고, 구동자조차 교대할 수 있어야 했습니다.

④ 매달 진화하는 새 AI 모델을 즉시 실측·투입하고 싶었습니다

DeepSeek V4.1 Flash, Gemini 3.8 Flash, GLM 5.3, Qwen 3.8 Max, Xiaomi MiMo V2.6 Pro 등 새 모델이 쏟아집니다. 소문이나 벤치마크 점수만 믿고 넣는 대신, 동일한 기준 과제로 정량 평가해 통과한 모델만 적재적소에 배치하는 구조를 원했습니다.

그렇게 세운 파이프라인 5대 목표 (`Docs/2026-09-29-hermes-multi-agent-pipeline-design.md`)

GOAL 01

최적 비용

품질 타협 없이 작업당 총비용(재시도·리뷰 포함)을 최적화하고, API 환산액과 구독 배분액을 분리 계측합니다.

GOAL 02

최고 품질

TDD 선행 실패 강제, 타사 모델 교차 리뷰, FD3 런타임 증거 게이트, Opus 최고 추론 판정으로 결함을 걸러냅니다.

GOAL 03

전 과정 자동화

요구사항 접수부터 설계·명세·테스트·구현·리뷰·수정 루프·커밋·보고서까지 파일 기반으로 자동 실행합니다.

GOAL 04

다중 공급사 활용

Anthropic, OpenAI, Google, DeepSeek의 강점을 조합해 사용량 병목을 깨고 독립적 시각을 확보합니다.

GOAL 05

AI 환경 지속 반영

설정 파일(roles.json)과 격리 평가 하네스를 통해 신규 모델과 추론(effort) 정책을 검증 후 즉시 반영합니다.

03 / DESIGN PRINCIPLES & TDD CONTRACT

타협하지 않는 6대 설계 철칙과 RED · FROZEN · GREEN 계약

프롬프트로 "잘 좀 해줘"라고 부탁하는 대신, 어기면 파이프라인이 즉시 멈추는(Fail-Closed) 기계적 규칙으로 설계했습니다.

STEP 01 · VALID RED

구현 전엔 반드시 "올바른 이유"로 실패해야 한다

제품 코드가 아직 없으므로 비즈니스 테스트는 실패해야 합니다. 단, 오타나 ImportError로 죽은 가짜 실패는 거부합니다. 테스트 본문(body)에 진입해 AssertionError(예: 200 기대 vs 404 응답)로 실패한 것만 진짜 RED로 인정합니다.

rawTestExit = 1 && gateExit = 0 (assertion_failure 필수)
STEP 02 · FROZEN MANIFEST

비준된 테스트와 해시는 구현 중 절대 바꿀 수 없다

테스트가 작성되면 수용 기준(F01~F03, B01~B06)과 테스트 ID 매핑을 사람이 비준(Ratify)하여 SHA-256 해시로 얼립니다. 제품 코드를 짜는 Codex가 테스트를 살짝 고쳐서 통과시키려 하면 guard no-test-change가 즉시 적발해 원상 복구합니다.

foundationManifestHash / businessManifestHash 동결
STEP 03 · DETERMINISTIC GREEN

모든 테스트 통과 + AST 린트 + 2회 동일 빌드

구현이 끝나면 동결된 기반·비즈니스 테스트가 100% 통과해야 하고, demo-lint.py(AST 정적 검사)와 demo-build.py(2회 연속 빌드 시 바이트 단위 SHA-256 완전 일치)를 모두 통과해야만 리뷰 단계로 넘어갑니다.

pass == discovered && buildHash1 === buildHash2

🔒 권한 우회 옵션 코드 레벨 원천 차단

--dangerously-skip-permissions, --yolo, bypassPermissions, --no-sandbox 같은 위험 플래그는 lib/command.js의 FORBIDDEN 정규식이 실행 전에 차단합니다.

🚫 조용한 자동 전환(Silent Fallback) 금지

1순위 AI가 사용 한도나 오류로 멈췄을 때 몰래 2순위 모델로 넘어가면 독립성과 비용 추적이 깨집니다. 반드시 exit 5(승인 대기)로 멈추고 승인된 규칙으로만 교체합니다.

📁 100% 파일·해시 기반 인계 (외부 의존성 0개)

Node.js 표준 모듈만 사용하여 공급망 공격 위험이 없으며, 모든 단계 인계는 디스크의 JSON/MD 파일과 SHA-256 해시로만 이루어져 언제든 재개 가능합니다.

04 / SYSTEM ARCHITECTURE

4계층 거버넌스와 파이프라인 엔진 내부 구조

지시는 위에서 아래로 내려가고, 암호학적 해시와 런타임 증거는 아래에서 위로 올라옵니다.

왜 4계층으로 분리했나요?

처음에는 사람이 직접 Hermes TUI에 명령을 입력했습니다. 하지만 엄격 검증 단계가 정교해질수록 중간 점검과 해시 확인 횟수가 늘어났고, 이를 해결하기 위해 사람과 Hermes 사이에 '위임 구동자(Driver)' 계층을 추가했습니다.

  • 1계층 — 사용자 (Human): 요구사항·정책 확정, 핵심 3대 승인/비준(SEQ1·SEQ5·SEQ9), 최종 브랜치 병합.
  • 2계층 — 위임 구동자 (Claude Code ↔ Codex): driver/run-hermes.sh로 비대화형 세션을 띄우고, 완료 후 원장·보고서·보호 매니페스트(17개 핵심 파일 해시)를 감사하며 다음 배치를 지시.
  • 3계층 — 지휘자 & 기계 게이트 (Hermes + pipeline/): bin/state, bin/guard, bin/checks를 호출해 단계 전이와 증거 봉투를 검증.
  • 4계층 — 역할별 AI 작업자 (Workers): 격리된 worktrees/ 안에서 부여된 최소 권한으로만 문서·테스트·코드를 작성하거나 리뷰.

07 / MECHANICAL VERIFICATION & EVIDENCE GATE

"끝났다"는 AI의 말을 믿지 않고, 런타임 증거로 판정합니다

파이프라인의 가장 독창적인 기술 자산은 Python/Django 런타임 내부에 훅(Hook)을 심어 전용 파이프(FD3)로 실행 증거를 뽑아내는 증거 게이트(`SPEC-v5.3`)입니다.

🔬 FD3 런타임 증거 파이프 (`hermes_evidence`) 원리

일반적인 CI는 테스트 프로세스의 종료 코드(0 또는 1)만 봅니다. 하지만 초기 프로젝트에서 ImportError나 설정 누락으로 러너가 죽어도 종료 코드는 1이 나오기 때문에 이를 정상적인 TDD 실패(RED)로 착각하는 치명적 문제가 있었습니다.

# pipeline/bin/checks --strict 실행 시 전용 파이프(FD 3) 연결
python -I -B adapters/hermes_evidence/django_runner.py \
  --settings demo.settings --nonce <64-hex> 3>&1

# FD3 스트림으로 방출되는 변조 불가능한 NDJSON 프레임 사슬:
1. run_start        (인터프리터 경로, Django/SQLite 버전, Nonce 결속)
2. settings_loaded  (실제 로드된 DB ENGINE / :memory: 확인)
3. discovery_item   (발견된 각 테스트 ID 등록)
4. case_start → case_body_start (setUp 통과 후 실제 테스트 본문 진입 증명!)
5. hook_witness     (발생한 AssertionError 객체 ID 및 traceback 발생 지점 포착)
6. case_body_end → case_result → case_stop → run_end

🛡️ 4중 방어선: 파일 가드 · 어댑터 가림 차단 · 무효화 행렬

1. 어댑터 가림(Shadowing) 원천 차단 (조각 4 S1 강화) 작업자 코드가 Worktree 루트에 hermes_evidence.py, .pyc, .so, 디렉터리, 심볼릭 링크를 만들어 증거 수집기를 가로채려 하면 실행 전에 ADAPTER_SHADOWED(exit 4)로 즉시 거부합니다.
2. 18순위 결정론적 증거 게이트 (`lib/evidence-gate.js`) Nonce 재사용, FD3 스트림 닫힘, JSON 스키마 위반, 시퀀스 누락, originLinkage 불일치, 매니페스트 테스트 누락 등을 1~18순위로 판정해 단 하나의 모호함도 허용하지 않습니다.
3. 16종 이벤트 연쇄 무효화 행렬 (`lib/state.js` `EFFECTS`) 승인된 명세 바이트가 바뀌거나 기반 테스트가 수정되면, 그 이후에 받았던 비준·체크·리뷰·판정 레코드에 invalidatedBySeq가 자동으로 찍혀 과거 통과 기록으로 커밋하는 것을 막습니다.
4. 3단계 원자적 커밋 & 크래시 복구 (`reconcileCommit`) 커밋 전 의도(commit-intent)를 기록하고 Hermes-Transaction 트레일러를 박아 커밋(commit-exec)한 뒤 재대조(commit-readback)합니다. 중간에 전원이 꺼져도 10개 복구 규칙으로 중복 커밋 없이 복원합니다.

10 / LESSONS LEARNED FROM 104 DECISIONS

직접 부딪히며 얻은 8가지 엔지니어링 교훈

이론적인 설계가 아니라, 실제 실패와 중단(D-01~D-104)을 겪으며 파이프라인 코드로 굳어진 실전 지혜입니다.

LESSON 01 · D-46

모델을 탓하기 전에 하네스와 패킷을 먼저 의심하라

DeepSeek의 초기 실패는 모델 지능 탓이 아니라 파일 읽기 도구 부재와 과대한 단일 호출 범위 때문이었습니다. 도구를 맞추고 1파일 단위로 쪼개자 주력 작성자가 되었습니다.

LESSON 02 · SPEC-v5

"테스트 실패(exit 1)"만으로는 진짜 RED를 증명할 수 없다

빈 프로젝트에서는 설정이나 임포트 에러로 죽어도 종료 코드가 1입니다. 기반(Foundation) GREEN을 먼저 통과시키고, FD3 훅으로 본문 AssertionError를 확인해야 진짜 TDD가 됩니다.

LESSON 03 · CLAUDE_LEAN

CLI 기본 오버헤드만 꺼도 프롬프트의 80%가 줄어든다

Claude CLI 호출 시 전역 MCP·스킬·슬래시 명령·훅이 자동 로드되며 호출당 약 60K 토큰을 먹고 있었습니다. CLAUDE_LEAN 플래그로 이를 차단해 약 12K로 줄였습니다.

LESSON 04 · D-95 & D-104

자유 서술 리뷰 대신 JSON 스키마와 줄 번호 `QUOTE`를 강제하라

마크다운 헤더 오타(## ## Reviewed)나 백틱 누락으로 리뷰가 무효 처리되던 문제를 --json-schema와 QUOTE {"file","line","text"} 기계 대조로 100% 해결했습니다.

LESSON 05 · D-03 & S1

파이프라인과 대상 프로젝트의 실행 경계를 철저히 의심하라

PYTHONPATH 순서 하나 때문에 작업자 코드가 검증 어댑터를 덮어쓸 수 있다는 점을 명세 리뷰(D-52)와 보안 강화(조각 4 S1)에서 잡아내 사전 거부 로직으로 막았습니다.

LESSON 06 · Effort Policy

추론 강도(Effort)는 높을수록 좋은 게 아니라 역할마다 다르다

모든 호출에 high를 쓰면 내부 추론 토큰(thinkingTokens가 출력의 85~96%)이 폭발해 65K 출력 한도에 걸립니다. 최종 판정(Opus)만 high로 고정하고 나머지는 medium과 분할 호출로 최적화했습니다.

LESSON 07 · D-104

식별자 형식(Schema)은 출구가 아니라 입구에서 검증하라

D-96 첫 리허설에서 대문자 D96이 들어간 runId가 strict-init을 통과한 뒤 SEQ6 증거 게이트에서 ^[a-z0-9-]+$ 정규식에 걸려 멈췄습니다. 즉시 입구 검증(2e9225c)을 추가해 재발을 막았습니다.

LESSON 08 · Accounting

모르는 비용을 $0으로 적지 말고, 축소된 독립성은 정직하게 공개하라

구독형 CLI의 미관측 비용은 unknown으로 남기고, 한도 때문에 같은 계열 모델이 리뷰했을 때는 보고서에 '독립성 축소'를 명시해 감사 신뢰성을 지켰습니다.

  • 핵심 도메인 2 — 100위안 보증금 및 30일 회수 유예 규칙: 지급 시 보증금 납부/차감 상태 추적, 교체·퇴사 시 30일 반납 대기 상태 관리 및 기한 초과 경보.
  • 핵심 도메인 3 — 인사 엑셀 업로드 비교 & 문제 데이터 모니터링: 인사팀 명단 업로드 시 입사·퇴사·이동을 자동 대조하고, 미반납·중복 할당·보증금 누락을 대시보드에 표시.
  • 데이터 보안 원칙 (규칙 4.7): 실제 임직원 이름·사번·IP가 담긴 원본 엑셀은 외부 AI 프롬프트에 직접 노출하지 않고, 스키마와 합성 픽스처 기반으로 안전하게 개발합니다.

12 / FAQ & GLOSSARY FOR AUDIENCES

발표 단골 Q&A 및 비전공자를 위한 친절한 용어 사전

다른 사람에게 이 프로젝트를 소개할 때 가장 자주 받는 질문과 핵심 용어를 정리했습니다.

💬 자주 묻는 질문 (발표 Q&A 대비)

Q1. 그냥 Claude나 Cursor 하나만 쓰면 더 빠르지 않나요?+
작은 프로토타입은 단일 도구로도 충분합니다. 하지만 ① 사내 핵심 업무 시스템처럼 수용 기준 누락이나 회귀 버그가 절대 없어야 하는 경우, ② 한 모델이 코드와 테스트를 같이 짜며 발생하는 착각 공유를 막아야 하는 경우, ③ 특정 구독의 5시간 사용 한도 때문에 개발이 멈추지 않아야 하는 경우에는 다중 공급사 분업과 기계적 증거 게이트가 필수적입니다.
Q2. AI가 테스트를 통과시키려고 테스트 코드를 지우거나 고치면 어쩌나요?+
원천적으로 불가능합니다. 테스트는 코드 구현 전에 먼저 작성되어 사람의 비준(SEQ5/SEQ9)과 함께 SHA-256 해시로 동결됩니다. 이후 코드를 구현하는 Codex 단계 직후에 bin/guard no-test-change 스크립트가 실행되어, tests/ 폴더 안에 단 1바이트의 변경이라도 감지되면 즉시 원본 테스트를 복원하고 test-tamper.md(HIGH 결함)를 발행합니다.
Q3. 파이프라인을 돌리는 동안 사람이 계속 컴퓨터 앞에 있어야 하나요?+
아닙니다. 위임 구동자(Claude Code 또는 Codex)가 백그라운드로 Hermes를 실행하고 결과를 점검합니다. 사람은 오직 정책/명세 승인(SEQ1), 테스트 매핑 비준(SEQ5·SEQ9), 최종 병합(Merge) 시점에만 개입하며, 도중에 멈추더라도 모든 상태가 디스크 원장(state-history.jsonl)에 남아 있어 언제든 이어 달릴 수 있습니다.

📖 핵심 용어 사전

오케스트레이터 (Orchestrator · Hermes)+
오케스트라 지휘자가 직접 악기를 연주하지 않고 연주자들의 순서를 지휘하듯, 직접 코드를 짜지 않고 단계별로 알맞은 AI 작업자와 검증 스크립트를 호출·통제하는 사령탑입니다.
Git Worktree (격리 작업 공간)+
원본 코드 저장소를 건드리지 않고 별도의 폴더(worktrees/)와 전용 브랜치(agent/<run-id>)를 복제해 AI가 그 안에서만 작업하게 하는 안전장치입니다.
비준 (Ratification · SEQ5 / SEQ9)+
"요구사항 A는 테스트 함수 X로 채점한다"는 연결표(Manifest)를 독립 리뷰어들이 먼저 심사한 뒤, 최종적으로 사람이 직접 서명(승인 메시지 해시 기록)하여 동결하는 절차입니다.
FD3 증거 봉투 (Evidence Envelope)+
일반 화면 출력(stdout/stderr)과 분리된 3번 전용 통로(File Descriptor 3)를 통해 Python 테스트 러너 내부에서 실제로 어떤 함수가 실행됐고 어떤 단언(Assertion)이 실패했는지 변조 없이 수집한 데이터 묶음입니다.
